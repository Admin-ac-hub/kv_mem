# KV / VectorDB 自动批量提交报告

日期：2026-10-14。参考：[LevelDB 同步 WriteBatch](https://github.com/google/leveldb/blob/main/doc/index.md)。本轮实现不主动等待的 FIFO writer queue / group commit，保持同步持久化、原有 WAL 格式和 HNSW 算法。

> 历史测量说明：性能表、向量接口和原始验证描述的是 2026-10-14 版本。2026-11-04 已移除 HNSW/VectorDB；2026-11-07 又完成下述 KV 去锁改动，未重测性能。因此本文吞吐及延迟数字不能作为去锁后的测量结果。

## 2026-11-07 当前 KV 并发补充

WriteQueue 的 `active_` 保证同一时刻只有一个组首执行提交，grouping 开/关均成立；
队列锁只用于准入、选组和完成通知，提交时释放。Close 先 StopAndDrain，Open/Close 由
生命周期锁串行化，因此移除额外的 `write_mu_`。

SkipList 后继改为 `std::atomic<Node*>`，高度和计数同样原子化。唯一写者先初始化不可变
载荷与全部后继，再从底层向高层 Release store 发布，读者 Acquire load 遍历；无需 CAS。
相同 internal key 的覆盖用新节点替换，旧节点保留到表销毁，读请求固定 Version 保住表的寿命，
因此移除 `memtable_mu_`。节点安全发布与整组可见性分开：全部节点装入后才发布 `last_sequence_`。

当前共 6 把线程锁；普通 Get 内存命中无显式 mutex，常规提交组首涉及队列锁和版本锁。
原子 shared_ptr 不保证底层无锁。Debug、Release、ASan/UBSan、TSan 均 8/8 通过，
具体覆盖与原始日志见 [当前验收记录](KV_CLOSURE_PLAN.md#2026-11-07-原子发布与去锁验证)，
锁职责见 [README 并发模型](../README.md#并发模型)。本轮未做吞吐对比。

## 2026-10-14 实现与接口（历史）

`Put/Delete/Write/PutVector` 仍为同步接口。KV 和 VectorDB 共用内部 `WriteQueue`：排队和完成通知持队列锁，WAL/MemTable/HNSW 提交不持该锁。组首线程只合并已排队的 FIFO 前缀，单请求直接使用原批次；每个原请求保持完整、不拆分，组内操作保持原顺序。调用期间不得由其他线程修改同一个 WriteBatch。

- `Options::enable_write_grouping=true`；关闭时每组只有一个原请求。
- `Options::write_group_max_bytes=1 MiB`，限制合并后的操作编码 payload，不含 WAL header。必须大于零；大于上限的合法原批次单独提交。
- `WriteBatch::EncodedSize/Reserve/Append` 用于尺寸检查和合并；Append 支持自追加，Encode 预留对应容量。
- `DBStats::wal_sync_count/wal_committed_operations/max_wal_batch_operations` 按对象生命周期累计成功同步的次数、操作数和最大批次操作数，跨 WAL 切换与 Close/Open 累计；不统计空批次或恢复重放。后续 MemTable/维护失败不撤销已成功同步的 WAL 计数。
- Close 先关闭写入准入、排空已接收请求，再关闭文件、等待后台维护；Open/Close 串行化。等待时不持版本锁或索引协调锁。

各请求在入队前独立校验；组首再次检查编码和 sequence 范围。核心按剩余 sequence 预算截断合并前缀。整组只有一个 WAL record，完整校验与解码后才恢复；同步成功后整组更新 MemTable，再一次 Release store 发布最后的 sequence，读侧 Acquire 取得整组边界，Snapshot/Iterator 不会取得半批视图。普通读原子 pin 不可变 Version，WAL 同步不持版本锁。

VectorDB 在独占 coordination 锁之前排队；组首持该锁完成一次 KV 提交、原操作顺序的 HNSW 更新，组尾最多检查和重建一次索引。维护检查仍默认 4096 操作，允许超出至当前组结束。存在历史版本或 tombstone 时重建；纯新增且没有垃圾节点时跳过重建、重置检查计数，并保留递增的索引 sequence。显式 RebuildIndex 始终重建。测试 commit/index hook 的调用边界和 position 对应合并后的组。KV 失败保守返回整组 Unknown；KV 成功后索引失败返回整组 Committed + index error，并置 Dirty。提交前拒绝保留 NotCommitted。Close 与显式重建继续和索引视图协调。

WAL/Manifest 持久化错误继续阻止后续写入，重开后确认实际恢复结果。组装和提交的标准/非标准异常均有队列退出和唤醒路径；现有内存分配失败下不提供强异常回滚保证。

## 性能方法

对照基线为 `dc63d44`。同一份 `group_commit_bench.cpp` 分别链接归档基线的 Release 库和当时工作区的 Release 库；基线使用 `KV_GROUP_COMMIT_BASELINE` 适配没有新配置/统计字段的旧头文件。旧实现同步数通过已有 WAL sync hook 计数，所有成功运行与实际成功同步对应；新实现直接读取新增统计。编译器、平台、源码与二进制 hash 和参数见 [最终 metadata.json](benchmark_results/20261014-group-commit/measurements-final/metadata.json)。

- KV：100,000 条，100 字节 value；VectorDB：6,000 条，128/768 维，固定数据种子，M=16、ef_construction=200、默认重建阈值 4096。
- 1/2/4/8 线程，原请求 batch=1/32，MemTable=1024、L0 limit=4；所有场景必须有至少两次 Flush 和一次 Compaction。
- 旧实现、新实现合并关闭/开启，各预热一次，再做七轮配对对照；轮次轮换三种变体的执行顺序。测量串行运行，期间不运行构建和测试。
- 前台吞吐计时从统一释放 worker 到 join，包含数据生成、KV 提交、索引更新及触发的重建；另计包含 Close/后台收尾的 wall 吞吐。Open 不计时。
- 请求 P50/P99 从真实 Put/PutVector/Write 调用开始至返回采样，包含队列等待。batch=32 的延迟是整次原请求的延迟，不除以操作数。
- 每次测量后用纯 KV 重开并逐条校验全部 value/向量编码；验证时间不计入吞吐。索引重建、查询一致性和崩溃后重建由向量回归单独验证。
- 采用七轮配对吞吐比的中位数，10,000 次 bootstrap，固定种子 20261014，取双侧 95% 区间。只有区间下界大于 1 才声明稳定提升，不删除异常轮次。

完整保留了两轮实现的测量。初版仍每 4096 次操作无条件重建，768 维 / 4 线程的前台吞吐相对旧实现比为 1.0013，95% 区间 [0.9929, 1.0037]，未通过验收；原始数据见 [初版 raw.csv](benchmark_results/20261014-group-commit/measurements/raw.csv)。最终版本增加单请求快速路径，并将自动维护改为到达阈值后有垃圾才重建，重新执行全部场景。后者改变了自动重建的触发策略，因此向量端到端收益不能全部归因于 WAL 合并；最终 ON/OFF 对照用于衡量同一维护策略下合并的额外收益。

## 最终实测结果

**整体严格性能验收未通过。** KV、128 维向量及 768 维 / 8 线程均通过；768 维 / 4 线程相对旧实现稳定提升，但 ON/OFF 前台区间 [0.9963, 1.0213]、含 Close 区间 [0.9963, 1.0213] 跨过 1，不能声称该场景的自动合并有稳定额外收益。没有选择性重跑或删去轮次。

最终共 576 次运行：24 个场景 × 3 个变体 ×（1 次预热 + 7 次测量），所有运行均逐条验证重开后的数据。原始数据、摘要与判定分别见 [raw.csv](benchmark_results/20261014-group-commit/measurements-final/raw.csv)、[summary.json](benchmark_results/20261014-group-commit/measurements-final/summary.json)、[acceptance.json](benchmark_results/20261014-group-commit/measurements-final/acceptance.json)。
