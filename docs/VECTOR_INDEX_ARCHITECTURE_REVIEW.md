## 2. V1（阻塞）段路由方案自相矛盾

### 2.1 问题

方案在四个地方对「一个条目属于哪个段」提出了要求，而这四个要求无法同时被 §4 的路由方案满足：

| 位置 | 要求 |
| --- | --- |
| §4 | 路由 = **thread-local 绑定**：`writer_index()` 是首次使用时建立的线程局部变量 |
| §7 | 「用**该段对应的 SSTable 条目**重建这一段」 |
| §10 | 「首次打开旧库时，从 SSTable 条目**重建所有段**」 |
| R5 | 快照头里存 `covered_sequence` + `covered_files`，不匹配则**只重建该段** |

thread-local 绑定**不是 key 的纯函数**。它取决于运行时哪个线程先碰到哪个 key，重启后无法复现，也无法回答「哪些 SSTable 条目属于段 i」。因此 §7 的单段重建、§10 的迁移、R5 的覆盖集校验都缺一个前提。

方案把 thread-local 绑定选在热路径上是对的（省一次 hash、零争抢），但它没有意识到这个选择把重建和迁移一起堵死了。

### 2.2 建议

**改为 `hash(key) % P`。** 收益不止于修好重建：

- 路由变成 key 的确定性纯函数 → §7 / §10 / R5 全部成立；
- **同一个 key 的所有版本落在同一段** → §5 的跨段版本裁决问题整体消失（见 V2），段内版本表即可自足；
- 不引入新的状态，不需要持久化任何路由表。

代价是写线程不再有独占段，需要重新论证 P 的取值（见 2.3）。

### 2.3 P 的取值需要重新论证

方案 §3.2 固定 **P = 写线程数，上限 8**。这在 thread-local 路由下是最优的（每个写者独占一段，零争抢），但在 hash 路由下不是。

hash 路由下写线程按 key 落段，这是一个球箱问题。P = T = 8 时：

```
期望被占用的段数 = P × (1 − (1 − 1/P)^T) = 8 × (1 − (7/8)^8) = 5.25
```

也就是 8 个写线程里平均只有 5.25 个在真正并行，其余 2.75 个在等锁 —— **损失约 34% 的并行度**。P = 32、T = 8 时期望占用 7.17 段（89.6%），P = 64 时 7.57 段（94.6%）。

但 P 增大会直接抬高 §3.3 承认的查询 fan-out 成本。**这是方案完全没有处理的权衡**：P 小则写并行度低，P 大则读 fan-out 贵。

这个权衡无法在纸面上定，需要在阶段 3 实测。建议把它写进 §15 未决问题 2，并把默认值从「P = 写线程数」改成「P = 4 × 写线程数」，同时在阶段 3 的验收里同时报 P ∈ {8, 16, 32} 的写吞吐与查询延迟。

## 3. V2（阻塞）跨段版本裁决规则不成立

### 3.1 问题

§5 规则 2 给出的「最简且正确的规则」是：

> 按 `key` 在所有段中取 `sequence ≤ read_sequence` 的最大者（无论是否 tombstone），然后丢弃 tombstone 条目。

这条规则对**归并层已经收到**的候选是正确的，但归并层只能看到各段返回的局部 top_k。段内搜索按距离截断，**不保证返回该 key 的最新版本** —— 尤其是当最新版本是 tombstone 时。

### 3.2 反例（可构造，且是常见情形）

设 key `k` 有两个版本，且路由把两个版本分到了不同段：

- 段 0：`(k, seq=10, live)`，图里有节点，向量与查询接近；
- 段 1：`(k, seq=20, deleted)`，版本表里有 tombstone，但**图里没有节点**（`MarkDeleted` 不建节点，见 `src/hnsw_index.cc:474-494`）。

查询落在 `k` 的旧向量附近，`read_sequence = 100`：

1. 段 0 搜索：`IsVisible(node@seq10, 100)` 检查段 0 的版本表 `{10: live}`，判定**可见**，返回 `k`；
2. 段 1 搜索：没有任何与 `k` 相关的节点参与距离排序，因此**不返回 `k`**；
3. 归并层看到的候选里只有 `k@seq10`，按规则取「最大可见版本」得到 `seq10` → **返回一个已被删除的 key**。

这正是方案 R3 标注为「高」的风险，但它给的缓解措施（「§5 规则 2」）并不能防住。

### 3.3 修法

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **(a) 采纳 V1 的 hash 路由** | 同 key 所有版本同段 → 段内版本表即可正确裁决；跨段只需按 key 去重（每个 key 只出现在一个段里） | **推荐**。一次改动同时修掉 V1 和 V2，零额外状态 |
| (b) 保留 thread-local 路由 | 归并层必须能问「`k` 的最新版本是什么」→ 需要全局 key→最新版本映射，且与各段插入保持原子 | 等于把版本表拉回全局，抵销 §3.1 的下沉，且引入新的跨段锁 |
| (c) 段内不按距离截断 | 对所有被候选集覆盖到的 key 返回最新版本 | 无法保证覆盖，不成立 |

`(a)` 之后 `HNSWSegment::Search` 的行为与今天单图的 `IsVisible`（`src/hnsw_index.cc:264-281`）完全一致，可以直接复用已验证的逻辑。

## 4. V3（必须重写论证）§1.3 的 FLOP 推导

### 4.1 结论先给

**「5 万条/s 不可达」这个结论成立，但 §1.3 的两个关键数字都不是实测，且「约为本核 NEON 峰值的 10%」是错的。**

### 4.2 实测：距离内核的真实速率

用 `tools/hnsw_partition_probe kernel`（新增，见 §6）在同一容器内测同一内核（768 维、L2、NEON 后端、f64 `vmulq_f64/vaddq_f64` 非 FMA），三种访存模式各 5 轮：

| 访存模式 | 说明 | 5 轮 GFLOP/s | 中位数 |
| --- | --- | --- | ---: |
| `hot` | 热查询 + 64 向量工作集（全在缓存），**纯计算上限** | 8.58 / 9.16 / 9.19 / 8.67 / 9.33 | **9.16** |
| `stream` | 两个操作数都顺序推进 | 7.00 / 8.07 / 8.60 / 8.66 / 8.08 | 8.08 |
| `hnsw` | 热查询 + 20k 数组中随机目标（**HNSW 实际访存模式**） | 3.80 / 3.54 / 4.05 / 1.98 / 2.58 | 3.54 |

参数：`dim=768`、`iterations=200000`、FLOP 口径 = `2 × dim`。

**该内核的实测计算上限是 ~9.2 GFLOP/s，不是 47 GFLOP/s。** 方案隐含的峰值（因为 4.7 是它的 10%）对 f64 非 FMA NEON 不成立。

### 4.3 距离计算次数：已实测，模型低估 3.07 倍

给 `HNSWIndex::Distance` 加了编译期可关的计数器（`-DKV_HNSW_DISTANCE_COUNTER=ON`，
默认构建无计数器、无额外分支），用 `hnsw_partition_probe distance` 实测：

| 量 | 方案取值 | 实测（n=20000, dim=768, M=16, ef_c=200, i.i.d. Gaussian, NEON） |
| --- | --- | --- |
| 距离计算次数/插入 | `ef_c × M = 3,200` | **9,810.6**（稳态后半段均值；三次运行逐位相同） |
| 分布 | — | p50 = 9,766，p90 = 11,365，max = 16,045 |
| 单次插入 FLOP | 4.9 MFLOP（模型） | **15.07 MFLOP** = 9,810.6 × 1,536 |
| 达到的速率 | 4.7 GFLOP/s（由模型反推） | **5.36–5.67 GFLOP/s**（真实插入循环内，实测计数换算） |

**计数器本身零可测开销**：同一 20k 配置，无计数器 336.1 / 419.6 / 341.0 条/s，
有计数器 411.4 / 408.8 / 433.1 条/s —— 差异落在 VM 抖动内（2× 量级）。
距离计数是**确定性**的，可跨机器比较；吞吐不是。

### 4.4 重算（结论比原稿更强）

```
50,000 × 15.07 MFLOP = 753.5 GFLOP/s
753.5 / 5.4  (真实插入循环达到的速率) ≈ 140 核
753.5 / 9.16 (内核 hot 模式上限)       ≈  82 核
8 核 ≈ 8 × 411 ≈ 3,290 条/s
```

原稿说 52 核，实际是 **82–140 核**。原稿之所以算小，是因为分子（3,200 次距离）和分母
（4.7 GFLOP/s）被同一个模型同向压缩，比值侥幸落在同一量级。**现在两个量都是实测的，
误差不再互相抵消 —— 结论方向不变，但强度更高。**

### 4.5 建议（已执行）

1. ~~把 §1.3 的 `4.9 MFLOP` / `4.7 GFLOP/s` 标为模型值~~ → **已改为实测值**。
2. ~~删掉「约为本核 NEON 峰值的 10%」~~ → **已删除**，换成三种访存模式的实测数字。
3. ~~加距离计算计数器拿到实测值~~ → **已加**（`KV_HNSW_DISTANCE_COUNTER`，默认 OFF）。
4. §1.3 已注明：容器数字只用于定论量级，不作验收值。

## 5. V4 / V5 / V6 / V7

### V4 阶段 0 的 go/no-go 门限会被噪声击穿

§15 未决问题 1 定的门限是「ef = 512 掉超过约 1 个点」。按 §14 的测试计划（100 查询、Recall@10）：

```
判定总数 = 100 查询 × 10 = 1,000
p = 0.95 时标准误 SE = sqrt(0.95 × 0.05 / 1000) = 0.0069 → 0.69 个点
1 个点 ≈ 1.45 SE → 单侧假警报率约 7%
```

门限比噪声还小。本次实验把查询数提到 **300**（SE → 0.40 点），并把判定标准改成「超出运行间噪声」而不是固定 1 个点。建议 §14 同步修改。

### V5 增量重放的「sequence → 向量」解析不总成立

§6.1 的增量记录不含向量，重放时「从拥有该 sequence 的 SSTable 里取回向量」。但 compaction 会丢弃被淘汰的版本，此时该 sequence 的向量**已经不在任何 SSTable 里**。

后果：段里出现一个「有边、无向量」的节点，图结构不一致（邻居指向空洞）。

方案没有覆盖这个分支。需要明确：

1. 增量里也要记 tombstone 记录（否则快照之后被删除的 key 会在重放时复活）；
2. 重放时若某条 INSERT 的向量已不可解析，**必须连同该 node_id 的所有边一起丢弃**，不能只跳过向量。

这直接影响 R4 与 R5 的缓解措施。

### V6 写路径的串行段没有被量化 —— **已测量，担忧被证伪**

见 §1.2。方案 §8 明确保留 `write_mu_` 串行化 WAL + MemTable，但没有给这个串行段任何数字。
我当时的估计是「若它占 30%，8 段并行最多只有 ~2.9×」。**实测只占 4.7%。**

容器内用 `vector_bench` 隔离测量（6000 × 768、batch=256、MemTable=1024、L0=4、
`--require-maintenance`，各 3 轮取中位数）：

| 配置 | 吞吐 | 每条耗时 | Close | flush / compaction |
| --- | ---: | ---: | ---: | --- |
| A 完整（M=16, ef_c=200） | 267.0 条/s | 3,745 µs | 14.0 s | 6 / 1 |
| B 图插入近似免费（M=2, ef_c=1） | **5,663.4 条/s** | **177 µs** | 0.75 s | 6 / 1 |

B 把图插入压到接近零，剩下的就是串行段 + 维护。**上限 ~5,600 条/s，只占 A 的墙上时间的 4.7%。**

结论：**串行段不是瓶颈，3,000–5,000 条/s 的目标不被它封顶**（上沿 5,000 仍在 5,600 之下）。
A 的 95% 时间花在图插入（含重复构图）上 —— 正是本重构要消灭的部分。

A 还复现了 F1/F2 的量级与比例：F1 = 316.93 条/s、Close 占 62%；本次 267.0 条/s、Close 占 62%。

> 附带发现：`kv_bench`（无 HNSW 的纯 KV 路径）是 **batch=1**，每次 `Put` 一次 WAL fsync，
> 6000–20000 条、value=3084 B 时只有 2,134–2,894 条/s、平均延迟 412–469 µs/条。
> 与 `vector_bench` 的 batch=256 不可比。测串行段必须用同一 batch 口径，否则会高估串行成本一个数量级。

### V7 接口草图缺 `HNSWIndex::MarkDeleted`

§9 的 `HNSWIndex` 草图只有 `Insert` / `Search` / `ApplyDroppedVersions` / `FlushDeltas` / `SnapshotAll` / `Stats`，但现有的 `MemTable::Put`（`src/memtable.cc:15`）和 `MemTable::Delete`（`src/memtable.cc:45`）都调用 `vector_index_->MarkDeleted(key, sequence)`。

这个方法恰好是 V1/V2 的焦点（它必须按 key 路由到正确的段），草图里不能缺。建议补上并写明路由规则。

## 7. 阶段 0 实测结果（GO）

### 7.1 实验设置

新增探针 `tools/hnsw_partition_probe.cpp`（本报告唯一的代码改动，未触碰生产代码）。
「段」建模为一个独立的 `HNSWIndex` 实例 —— 结构上与方案 §3.1 的 `HNSWSegment` 一致（独立节点号、独立入口点）。

| 项 | 取值 |
| --- | --- |
| 语料 | 20,000 × 768 |
| 查询 | 300 条（按 V4，SE ≈ 0.40 个点） |
| M | 16 与 32 两组 |
| ef_c | 200 |
| P | 2 / 4 / 8 |
| 分片方式 | 固定种子的**随机** 1/P 子集（同时建模 thread-local 与 hash 两种路由，两者都与语料几何无关） |
| 后端 | NEON（容器内 linux/arm64） |
| 原始输出 | `bench_runs/stage0-partition/p{2,4,8}_m16.txt`、`p8_m32.txt` |

单图臂扫 ef ∈ {128, 256, 512}；分片臂扫每段 ef ∈ {16, 32, 64, 128, 256, 512}。

### 7.2 核心结果：召回不降反升

M=16、20k×768、P=8、每段 2,500 节点：

| 查询分布 | 单图 ef=128 | 单图 ef=256 | 单图 ef=512 | **P=8 seg_ef=64** | **P=8 seg_ef=128** | **P=8 seg_ef=256** |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| i.i.d. Gaussian | 0.7440 | 0.8697 | 0.9373 | 0.9357 | **0.9840** | 0.9983 |
| 共享中心聚类 | 1.0000 | 1.0000 | 1.0000 | 0.9987 | 1.0000 | 1.0000 |
| 独立中心聚类（OOD） | 0.5670 | 0.7310 | 0.8923 | 0.9087 | **0.9767** | 0.9990 |

M=32 同向（`p8_m32.txt`）：i.i.d. 单图 ef=512 = 0.9883，P=8 seg_ef=64 = 0.9857、seg_ef=128 = 0.9987；
OOD 单图 ef=512 = 0.8977，P=8 seg_ef=64 = 0.9310、seg_ef=128 = 0.9870。

**R1（归并后召回退化）不成立，实际方向相反。** 在全部三种分布、P ∈ {2,4,8}、M ∈ {16,32} 下，
同等每段 ef 的归并召回都高于单图。原因不是巧合：每个段在自己的 1/P 子图上做一次独立搜索，
归并等于把 P 份局部 top-k 并起来再排序，候选质量高于单图在同样 ef 下的候选质量。

### 7.3 召回上限也被抬高

OOD 是最能说明问题的一列：单图在 ef=512 只有 0.8923，而 P=8 在 seg_ef=128 就到 0.9767。
**单图在测试范围内够不到这个水平。** 这是分片带来的结构性收益，不是预算堆出来的。

### 7.4 代价与 iso-recall 对比

分片臂的 QPS 是**顺序** fan-out。因为各段等大，P 路并行 fan-out 的墙上时间 ≈ 单段耗时，
所以并行 QPS ≈ P × 顺序 QPS。**下表「推算并行」是推算值，不是实测** —— 探针没有线程池，
阶段 4 必须实测。

| 分布 | 单图（最优召回点） | QPS | P=8（等召回或更高） | 顺序 QPS | 推算并行 QPS | 召回差 | 推算加速 |
| --- | --- | ---: | --- | ---: | ---: | ---: | ---: |
| i.i.d. Gaussian | ef=512 → 0.9373 | 251.4 | seg_ef=64 → 0.9357 | 219.5 | ~1,756 | −0.0016 | **~7.0×** |
| 共享中心聚类 | ef=128 → 1.0000 | 4,174.3 | seg_ef=16 → 0.9980 | 1,467.2 | ~11,738 | −0.0020 | **~2.8×** |
| 独立中心聚类（OOD） | ef=512 → 0.8923 | 1,357.1 | seg_ef=64 → 0.9087 | 412.6 | ~3,301 | **+0.0164** | **~2.4×** |

三行里两行召回更高、一行低 0.2 个点（在 0.40 个点的 SE 内）。**并行 fan-out 之后分片在三个分布上都不输。**

### 7.5 P 的趋势：它同时是召回旋钮和代价旋钮

i.i.d.、M=16、目标召回 ≈ 0.937：

| P | 达到该召回的每段 ef | 顺序 QPS | 推算并行 QPS | 推算加速 |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 256 → 0.9533 | 285.6 | ~571 | ~2.3× |
| 4 | 128 → 0.9497 | 228.0 | ~912 | ~3.6× |
| 8 | 64 → 0.9357 | 219.5 | ~1,756 | ~7.0× |

召回上限也随 P 上升：i.i.d. 下 P=2 在 ef=512 只到 0.9867，P=4 到 0.9980，P=8 在 ef=256 就到 0.9983。

**结论：P 越大，同等召回下越快，召回上限也越高。** 这与 V1 里写侧的结论（P 越大，hash 路由的锁竞争越小）方向一致 —— 两侧都指向更大的 P。但 P 增大会同时抬高内存（§6 的 `O(查询线程数 × N)`）和归并开销，所以上限需要实测，不能无限加。

### 7.6 §3.3 的悲观论断需要修正

方案 §3.3 说「单段变小省下来的抵不过 ×P 的开销」。实测：

- 顺序 fan-out 的 QPS 损失是 **1.8–14×**，不是 P 倍 —— 因为单段搜索确实便宜了很多（i.i.d. ef=128：单图 589.6 qps，P=8 顺序 153.3 qps，仅 3.85×）；
- 并行 fan-out 之后，如 §7.4 所示，三个分布上都不输单图。

方向判断对（fan-out 不能顺序做），量级过于悲观。

### 7.7 本实验没有覆盖的

1. **V2 的跨段版本裁决**：语料无版本、无 tombstone，归并退化为纯 top-k。这正是 §3 指出的漏洞所在，**阶段 0 的 GO 不能替代对 V2 的修复**。
2. **真实并行 fan-out 延迟**：§7.4/§7.5 的并行列是推算值。
3. **绝对性能**：数字来自容器（linux/arm64 VM），只用于定论量级，不是验收值；实测中 `hnsw` 访存模式的内核速率抖动达 2×（V3 §4.2）。
4. **段的额外开销**：真实 `HNSWSegment` 还带自己的版本表、锁和文件 I/O，探针里没有。

### 7.8 阶段 0 判定

**GO。** 方案的阶段 3–4（P 个段 + 并行 fan-out）值得建，且 §11 里「召回 = 未知」那一行可以填成
「**不退化，在 OOD 上显著提升**」。但阶段 3 的路由实现必须按 V1 改成 `hash(key) % P`，
否则 §3 的版本复活问题会在阶段 4 的归并里直接暴露。
